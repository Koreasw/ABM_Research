# 계획서 — B15-3: H1 풀 배정 리플레이 검증 (이연 구현)

> **지위**: B15-3의 계획 정본 (2026-08-11, Fable 5 작성). A7-a 설계(`design_a7a_gates.md`)의
> 사용자 결정 #4에 따른다: *"H0 검증 로직의 복제-이식이 아니라, H1 구현이 모두 끝난 다음
> 구현된 H0 검증 로직을 참고해 H1의 검증 로직을 신규 구현한다."*
> 이 문서는 **그 구현을 위한 계획**이며, 트리거 조건(§3)이 충족되기 전에는 착수하지 않는다.

---

## §1. 무엇을 지키는 게이트인가 — 위협 모델

주문→라이더 배정의 **상류 규칙**이 무게이트다. A5-c 리뷰의 실측: 결과 JSON의 전 주문
`rider_type`을 CAR로 변조해도 B1~B11 전건 PASS. 배정 규칙(비용 우선순위 캐스케이드,
fallback)이 회귀해도 어떤 게이트도 울리지 않는다 — H0 쪽은 A7 게이트가 이를 지키고
있으나 H1은 무방비다.

B15-3의 목표: **기록된 시각들로 라이더 풀을 이산사건 리플레이**하여, 모든 주문의
`rider_type`과 `was_fallback`이 배정 규칙에서 재현되는지 검증한다(H0 A7의 H1 대응물).

## §2. 왜 이식이 아니라 신규 구현인가 (기술 근거)

H0의 `check_assignment_replay`(verify_h0.py)는 다음 지점에서 **H0의 의미론에 결합**되어
있다 — 그대로 이식하면 H1에서 조용히 틀린다:

| 결합점 | H0 | H1 (다른 점) |
|---|---|---|
| 라이더 해제 시각 | `exited_at_sec` = **배달 완료 후 하강·퇴장**(주문당 라이더가 끝까지 점유) | 인계 라이더는 **로비 인계 후 조기 퇴장** — 해제가 훨씬 이르고, 로봇 대기(`robot_wait`)가 퇴장 시각에 개입 |
| return_leg 이연 | `dist_m / speed` 복귀 주행을 다음 틱 경계로 양자화 | 동일 규칙이 적용되는지 **H1 구현 완료 후 확정** 필요 |
| 동일-틱 하위집합 판정 | 같은 틱의 해제 부분집합 S에 대해 캐스케이드 재현 허용 | 인계 체인의 틱 순서(로봇→라이더, A4 골든패스)가 새 동일-틱 조합을 만든다 |

즉 리플레이의 **뼈대(이산사건 + 캐스케이드 + S-판정)는 참고**하되, 해제 의미론은 H1
정본에서 새로 유도해야 한다. 그리고 그 정본은 **H1 구현이 전부 끝나야 동결**된다 —
이것이 이연의 이유다.

## §3. 트리거 — 언제 착수하는가

**Phase A 종료 후**: ①A7-a 구현 완료(B12~B18 중 B15-3 제외분) ②A7-b 84 run 전수 PASS
③`checklist_visual_h1.md` 15항목 육안 서명. 이 셋이 끝나면 H1 상류 규약이 동결된 상태다.

권고 시점: **Phase B(H2) 착수 직전 또는 초입.** §A5-c-④ #6(_guard 공용화)·#7(게이트
이름 이중화)·#8(실구동 테스트)이 Phase B 사안이므로, B15-3 구현을 **검증기 공용화
작업과 같은 묶음**으로 처리하면 리플레이 골격(이산사건 엔진·캐스케이드)을 verify_h0와
공용 모듈로 빼는 작업이 자연스럽게 함께 된다 — 복제 부채를 아예 만들지 않는 경로.

## §4. 범위

- **포함**: H1 결과 JSON에 대한 배정 리플레이 게이트(가칭 B15-3, verify_hr 편입) —
  `rider_type`·`was_fallback` 전 주문 재현 + 풀 보존(종료 시 free == initial).
- **포함**: 음성 회귀 — 전 주문 CAR 변조 → FAIL(A5-c가 실측한 조작 그대로),
  `was_fallback` 반전 → FAIL.
- **제외**: FCFS 로봇 배차(이미 B7이 소유), 건물 안 체인(B2), 상류 시계열 단조(B15-1)·
  도착 재구성(B15-2 — A7-a에서 구현됨).

## §5. 단계

| # | 단계 | 산출물 |
|---|---|---|
| 1 | **H1 해제 의미론 추출** — 인계 라이더의 ready→dispatch→…→exit 체인에서 풀 해제 시각·return_leg 적용 여부를 코드 정본(handoff_rider.py, rider_pool.py)에서 유도, 문서화 | 의미론 노트(구현 로그 §B15-3-①) |
| 2 | **H0 A7 로직 해부** — 참고 구현의 구조(이산사건 루프·S-판정·보존 검사)를 공용 가능 부분과 H0 고유 부분으로 분해 | 분해 표 |
| 3 | **공용 골격 설계** — Phase B #6과 함께: 리플레이 엔진을 공용 모듈로, H0/H1이 각자의 해제 의미론만 주입 | 모듈 설계(±1쪽) |
| 4 | **구현 + 음성 회귀** — H1 게이트 + 조작 테스트 2건 이상 | verify_hr B15-3 + 테스트 |
| 5 | **전수 검증** — 4티어 표준 결과 PASS + 84 run 배터리에 편입 | 게이트 리포트 |

## §6. 완료 기준

4티어 표준 결과에서 B15-3 PASS · 음성 조작 전건 FAIL 검출 · 전체 스위트 green ·
구현 로그에 §B15-3 기입 · 리플레이 골격이 verify_h0와 공용(복제 0줄).

## §8. 수용된 공백 (사용자 결정에 따른 기록)

트리거 충족 전까지 **rider_type 변조는 무게이트**다. 부분 방어: B15-1(시계열 단조)·
B15-2(도착 재구성 — 틀린 rider_type이면 speed가 달라져 `arrival = dispatch + dist/v`
재구성이 어긋나므로 **속도가 다른 유형 간 변조는 간접 검출된다**). 속도가 같은 유형 간
변조와 `was_fallback` 변조가 남는 공백이며, 이는 Phase A 산출물이 아직 논문 수치로
인용되기 전이라는 시점 특성상 수용 가능하다고 판단, 사용자 결정으로 확정됐다.
