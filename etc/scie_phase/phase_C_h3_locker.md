## §0. 이 Phase를 처음 보는 사람을 위한 배경

H1·H2의 공통 한계: 라이더가 **로봇을 기다려야 한다**(동기 핸드오프). H3는 이 결합을
끊는다 — 라이더는 로비의 **자동 도킹 락커**(잠금 보관함)에 음식을 넣고(도킹, 평균
20초) **즉시 떠난다**. 로봇은 나중에 락커에서 꺼내(픽업, 평균 15초) 배달한다. 라이더와
로봇이 만날 필요가 없는 **비동기** 핸드오프다.

세 이해관계자에게 갖는 의미:
- **라이더**: 체류 시간이 도보+20초로 최소화 — 4모드 중 라이더 후생 최상 후보.
- **고객**: 음식이 락커에서 대기하는 시간만큼 배달은 오히려 늦어질 수 있음(로봇이 바쁘면).
- **빌딩**: 락커 설치비(CAPEX)가 든다 — "라이더 시간 절약이 락커 투자를 정당화하는가"가 RQ4(break-even w\*)의 질문이고, 이 Phase가 그 실험 재료를 만든다.

락커가 만석이면 라이더는 Phase B에서 만든 **H2 경로로 우회(fallback)** 한다 — 관리자
알림·balk 규칙이 그대로 적용되어, fallback 라이더도 W_est를 확인하고 대기 비용이 임계
이상이면 직접 배달로 전환한다(2026-07-23 개정 정합). 신규 경로가 아니라 기존 경로
재사용이므로 구현이 가볍고, 이미 검증된 코드를 탄다.

**이 Phase의 필수 용어** (상세: research_plan_scie.md §0):
- **M / V_max**: 락커 칸 수(기본 4, 스윕 {2,4,8}) / 칸 하나의 부피 상한(기본 100 — 주문 부피 VOL의 95퍼센타일이 ~70이라 대부분 수용). 주문 부피가 빈 칸들의 V_max를 전부 초과하면 그 주문도 fallback.
- **보관 한도**: 신선식품 품질 기준 30분. 초과 시 이벤트 기록(주문 자체는 지연 인도).
- **U_locker / 도킹 실패율**: 락커 점유율 / 빈 적합 칸이 없어 fallback한 비율 — 락커 sizing의 판정 지표.
- **E4 스윕**: 락커 자원(M × V_max)의 격자 실험 — C3 실무 기여(가이드라인)의 락커 축 재료.

### ★ 미결 결정 — `delivered`를 **투입**으로 볼 것인가 **수령**으로 볼 것인가

> R8 결정 #24에서 이월된 **유일한 미결 결정**이다(2026-08-06 등재).
> Step C0 설계 동결에서 **사용자 확인 항목으로 올릴 것.** 그 전까지 이 문서의
> 어떤 수치도 T_e2e를 확정 인용하면 안 된다.

H0~H2는 라이더/로봇이 고객에게 직접 넘기므로 `delivered` 시점에 모호함이 없다.
H3은 사이에 **락커**가 끼어서 후보가 둘이다:

| 후보 | `delivered` = | 종료 조건 | 대가 |
|---|---|---|---|
| **A. 사물함 투입** ← **권장** | 로봇이 칸에 넣은 순간 | H1과 동일(라이더 퇴장 ∧ 로봇 홈) | 고객 수령 지연이 T_e2e에서 빠진다 → **별도 KPI `T_pickup`으로 분리 보고** |
| B. 고객 수령 | 고객이 칸을 연 순간 | + "락커 전 칸 비움"까지 대기 | ①`CustomerAgent`를 **능동화**해야 한다(현재 완전 수동, `simulation/agents/customer.py`) ②종료가 고객 수령까지 늘어져 run이 길어진다 ③**T_e2e에 수령 지연이 섞여 H0~H2와 비교 가능성이 깨진다** |

**A를 권장하는 이유는 ③이다.** 이 논문의 주장은 모드 간 비교인데, H3에만 고객
행동 지연이 섞이면 그건 시스템 성능 차이가 아니라 **측정 대상이 다른 것**이 된다.
수령 지연은 없애는 게 아니라 `T_pickup`으로 **분리해서** 보고하면 정보가 보존된다.

**A를 택하면** 아래 완료 기준 3의 "락커 전 칸 비움" 종료 조건은 **불필요**해지고,
H3 종료 조건은 H1과 글자 그대로 같아진다. **B를 택하면** `_carriers_settled()`에
네 번째 항을 추가하고 `CustomerAgent`에 능동 수령 FSM을 신설해야 한다.
`D1 락커 보존`(도킹 = 수거 + 잔여 0)은 **어느 쪽이든 그대로 유효**하다 —
A에서는 종료 후 사후 검사, B에서는 종료 조건 그 자체가 된다.

**완료 기준**:
1. 전체 스위트 green + **H0·H1·H2 비트 동일성**.
2. Step C0 설계 동결 문서화 + 사용자 확인.
3. H3 골든패스 2케이스 0-tick 일치.
4. D-게이트 **코퍼스 28 × 3 seed = 84 run** 전수 PASS *(구 38 — 결정 #21)*.
5. 단조성·극한 PASS, E4 스윕 CSV 산출, 진행 로그 기록.

## §2. Step별 상세

### Step C0 — 설계 동결 (배정: 세션(오퍼스)/max 직접 + **사용자 확인 1회**, ~0.5일)

**동결할 규칙과 권장안**:

| # | 규칙 | 권장안과 근거 |
|---|---|---|
| C0-1 | **fallback 진입 시점** | 라이더가 락커 앞 도착 tick에 "부피 적합 빈 칸" 존재를 판정 — 없으면 즉시 H2 경로로 이동(알림·balk 규칙 적용; 예약·재시도 없음, 단순성) |
| C0-2 | **로봇 수거 우선순위** | 보관 시간 최장 우선(FIFO — 신선도 관점에서 자연스럽고 FCFS 관례와 통일). 동률은 주문 ID 오름차순 |
| C0-3 | **칸 배정 규칙** | 빈 칸 중 V_max ≥ VOL인 **최소 칸**(best-fit — 큰 칸을 작은 주문에 낭비하지 않음). M·V_max 스윕에서 배정 규칙은 고정 |
| C0-4 | **보관 30분 초과 처리** | 이벤트 기록만(관리자 개입 카운터) — 주문은 지연 인도로 계속 진행. 폐기 모델은 도입하지 않음(고객 renege 미모델링 원칙과 일관) |
| C0-5 | **도킹·픽업 난수 스트림** | 도킹 N(20, 5²)·픽업 N(15, 4²) 0-절단, 신규 3-워드 스트림 태그 `[0x6C6F636B('lock'), rng_seed, ord_id]` — 기존 스트림(도착·층·수단·보행자·인계) 무교란으로 CRN 유지 |
| C0-6 | **로봇의 H3 동선** | 픽업존 대기 → notify 수신 → 락커로 이동 → 픽업 15초 → 이후 H1과 동일(**공용 EV(EV3·EV4)** 상행·인도·복귀). 로봇 FSM에 TO_LOCKER·PICKUP 상태만 추가 |

**산출물**: 본 문서 §2에 확정 내용 인라인 추기(사용자 확인 날짜 병기).

### Step C1 — LockerAgent 구현 (배정: 오퍼스 / high, ~2일)

**왜**: 락커는 칸 상태(비어있음/점유(주문 ID, 보관 시작 시각))의 자료구조 + 부피 제약
+ 알림(notify) 이벤트가 얽힌 신규 에이전트로, 보존 불변식(도킹 = 수거 + 잔여)이 KPI에
직결된다.

**무엇을**:
1. `simulation/agents/locker.py` (현재 스텁) 구현:
   - `try_dock(order, vol)` → C0-3 best-fit 배정, 성공 시 점유 기록 + `notify(robot_pickup_zone)` 발신, 실패 시 False(라이더가 fallback).
   - `pickup(order)` → 칸 비움 + 보관 시간 기록.
   - 보관 30분 초과 감시(C0-4 카운터).
2. 계측: 시점별 점유 칸 수(U_locker 시계열), 도킹 실패(fallback) 건수, 보관 시간 분포.
3. `configs/modes/h3_locker.yaml`에 M·V_max·도킹/픽업 분포 파라미터 배선.

**산출물·검증**: locker.py + 단위 테스트(부피 경계·만석·동시 도킹 케이스).

### Step C2 — H3 라이더 플로우 + fallback 배선 + 로봇 확장 (배정: 오퍼스 / high, ~1일)

**무엇을**:
1. `HandoffRiderAgent` 상태 추가: WALK_TO_LOCKER → DOCK(20초) → WALK_TO_EXIT / (만석 시) → Phase B의 알림·balk 판단을 거쳐 WAIT_QUEUE 또는 FALLBACK_H0 경로로 합류(코드 재사용 — 신규 FSM 없음).
2. 로봇 FSM에 TO_LOCKER → PICKUP(15초) 상태 추가(C0-6), `control_system.py`에 notify 수신 → idle 로봇 배정(C0-2 우선순위).
3. 모드 게이트에서 `H3_LOCKER` 허용, 종료 조건 확장(락커 전 칸 비움 포함).
4. 주문 기록에 `docked_at_sec`·`locker_dwell_sec`·`fallback_queue=True` 필드 additive 추가.

**산출물·검증**: K50_1 `--mode h3 --audit` 스모크 완주, H0·H1·H2 비트 동일 확인.

### Step C3 — H3 KPI (배정: 소넷 / medium, ~0.5일)

**무엇을**: U_locker(평균·피크, orderspan 분모), 도킹 실패율, 평균 보관 시간, 보관
한도 초과 건수. 전부 additive.

### Step C4 — D-게이트 구현 (배정: 오퍼스 / medium + **오퍼스/max 리뷰 1회**, ~1일)

**무엇을**: `analysis/verify_h3.py` — C-게이트 상속 + 락커 전용 불변식:
- D1 **락커 보존**: 도킹 건수 = 수거 건수 + 종료 시 잔여 0 (전량 수거 확인)
- D2 **부피 무위반**: 전 도킹 건에서 배정 칸 V_max ≥ VOL, 위반 0
- D3 **best-fit 재현**: 기록으로부터 칸 배정을 재계산해 C0-3 규칙과 일치
- D4 **수거 순서 재현**: C0-2(보관 최장 우선) 위반 0
- D5 **fallback 정합**: 도킹 실패 라이더의 이후 기록이 C-게이트 큐 불변식을 만족
- D6 **보관 시간 정합**: locker_dwell = 수거 − 도킹, 30분 초과 건수 = 카운터 일치
- D7~D9: 기구학·윈도우·프로파일의 H3 버전
음성 케이스 포함 `tests/test_verify_h3.py`.

### Step C5 — H3 골든패스 2케이스 (배정: 오퍼스 / medium, ~1일)

**무엇을**: ①주문 1건 × 유휴 로봇 — 도킹 즉시 라이더 퇴장, 로봇이 notify 수신 →
픽업 → 배달의 전 체인(라이더 퇴장 시각이 배달 완료보다 **앞서는** 것이 H3의 서명임을
수기로 확인) ②주문 2건 × 칸 1개(M=1) — 첫 주문 도킹, 둘째 라이더 fallback → 큐 →
로봇 매칭의 혼합 체인 0-tick 대조.

### Step C6 — 단조성·극한 (배정: 소넷 / low~medium, ~0.5일)

**무엇을**: 단조성 — ①M ↑ ⇒ 도킹 실패율 ↓ ②V_max ↑ ⇒ 도킹 실패율 ↓ ③K ↑ ⇒ U_locker·
보관 시간 ↑. 극한 — M=1(사실상 전량 fallback → H2와 근사 일치해야 함: fallback 경로
자기 검증), V_max=50 < VOL 중앙값 부근(부피 제약 지배 상황).

### Step C7 — 배터리 + E4 락커 sizing 스윕 (배정: 소넷 / medium, ~1일)

**무엇을**:
1. H3로 **28 × 3 seed = 84 run** 전수, D-게이트 인라인 PASS.
2. **E4 스윕**: M ∈ {2, 4, 8} × V_max ∈ {50, 70, 100} × K ∈ {50, 100} × 10 seed —
   도킹 실패율·U_locker·라이더 체류의 격자표 산출(`results/scie/e4_locker_sizing.csv`).
   Phase D 본 실험의 락커 기본값(M=4, V_max=100)이 합리적임을 이 표로 사전 확인하고,
   C3 실무 기여(가이드라인)의 락커 축 재료로 넘긴다.

**시나리오 선정 주의(2026-08-03 H0 진단)**: 락커 동시 점유 피크를 만드는 것은
평균 부하가 아니라 **도착 버스트**다. H0 진단에서 건물 도착 프로세스의 CV²는
같은 K 안에서도 배수로 갈리고(패턴 분산 68%), peak10/mean 비도 1.11~2.86으로
편차가 크다 — 즉 K가 같아도 시나리오에 따라 필요한 칸 수가 달라진다. 따라서
E4의 각 K 칸을 시나리오 1개로 대표시키지 말고, **고·저 버스트 시나리오를
각각 포함**해 도킹 실패율의 범위(최악·중앙)를 함께 보고한다.

**선정 입력 (2026-08-04 경로·수치 정정)**: **`results/h0_stats/scenario_traits.csv`**
(v2 재생성본)의 `peak10_over_mean`·`ia_cv2`를 쓴다. *구 표기
`analysis/h0_insights/tables/…`는 R0 아카이브 때 이동했고, 그 안의 값은 v1 조건이라
선정 기준으로 부적합하다.* v2 코퍼스 실측: `ia_cv2` 최대 **K200_9 = 2.26**
(이어 K200_6 1.97 · K100_6 1.94), 최소 **K100_2·K100_5 = 0.82**. ⚠️ 이 CSV는
**primary 20개로 고정**돼 있어 **K300 8개가 빠져 있다** — extreme 티어까지 필요하면
`--tier all`로 재생성한 뒤 **반드시 primary로 되돌릴 것**(`h0_baseline_stats.py`가
`tier` 열로 정합을 검사한다).

## §4. 리스크·주의점

1. **M=1 극한의 자기 검증**: 전량 fallback 시 H2와 근사 일치해야 한다 — 불일치하면 fallback 배선 버그(Phase B의 C_th 극한(∞·0)과 쌍을 이루는 공짜 검증).
2. **보관 시간의 고객 비용**: H3에서 T_e2e에 "락커 대기"라는 신규 성분이 생긴다 — 배달 시간 분해 체계(A5 계보)에 locker_dwell 성분을 추가해 잔차 0 검증을 유지해야 한다(D-게이트 D7에 포함).
3. **로봇 1대 + 고부하에서 락커 포화 연쇄**: 락커가 버퍼 역할을 하다 만석 → fallback 폭주로 H2보다 나빠질 수 있음 — 버그가 아니라 RQ2 역전 메커니즘의 일부이므로 계측만 정확하면 된다.
4. **락커의 이득이 공용 EV 병목에 흡수될 수 있음**(2026-08-03 H0 진단, **2026-08-04 재판정**): H3는 라이더를 로봇 대기에서 해방시키지만, 배달 자체는 여전히 로봇의 **공용 EV(EV3·EV4) 왕복**에 묶인다. 카당 로봇 1대 제한으로 로봇 트립이 직렬화되므로, **고부하에서는 락커를 늘려도 U_locker만 오르고 배달 시간은 개선되지 않는 포화 구간**이 나타날 것으로 예측된다. ⚠️ *구 근거였던 "로봇 트립 수요가 K500부터 현 EV2 사람 보딩과 맞먹음(비율 1.05~1.48 at K1000)"은 **인용 금지** — v1 2EV 조건이고 K500·K1000은 코퍼스 밖이다. v2에서는 ①공용이 **2대**로 나뉘어 직렬화 압력이 절반이 되고 ②코퍼스 상단이 **K300**이므로, 포화 구간이 **v1 예측보다 높은 부하에서** 나타나거나 코퍼스 안에서는 아예 안 나타날 수 있다. 안 나타나면 그것 자체가 보고할 결과다.* E4 표에서 M↑에 대해 도킹 실패율은 내려가는데 T_e2e·보관 시간이 평평해지면 그것이 이 구간이며, 락커 sizing 가이드라인(C3)에 "EV 용량이 병목인 빌딩에서는 락커 증설의 한계 효용이 급감한다"는 경계 조건으로 기술한다.
