## §0. 용어와 약어 해설 (필독)

본 계획서 전체에서 사용하는 용어를 주제별로 먼저 설명한다.

### §0.1 연구 방법론 일반

| 용어 | 설명 |
|---|---|
| **ABM** (Agent-Based Model, 에이전트 기반 모델) | 시스템을 하향식 수식 하나로 기술하는 대신, 개별 행위자(라이더, 로봇, 승객 등)를 각각 독립된 "에이전트"로 프로그래밍하고 이들이 상호작용한 결과로 시스템 전체 거동이 창발하게 하는 시뮬레이션 방법. 본 연구의 핵심 방법론이다. |
| **Mesa** | 파이썬 기반의 ABM 구현 프레임워크(오픈소스). 본 프로젝트의 시뮬레이션 코드는 전부 Mesa 위에 구현되어 있다. |
| **tick** | 시뮬레이션의 최소 시간 단위. 본 모델은 1 tick = 1초로 진행되며, 매 tick마다 모든 에이전트가 한 번씩 행동한다. |
| **seed (시드)** | 난수 생성기의 초기값. 같은 seed로 실행하면 같은 결과가 재현된다. 시뮬레이션은 확률적이므로, 같은 조건을 서로 다른 seed 30개로 반복 실행하여 평균과 신뢰구간을 얻는다. |
| **RNG 스트림** | RNG(Random Number Generator, 난수 생성기)를 용도별로 분리해 놓은 것. 본 모델은 "주문 도착용", "층 배정용", "보행자용" 등 난수를 태그가 붙은 독립 스트림으로 분리하여, 한 실험 조건을 바꿔도 다른 부분의 난수가 흐트러지지 않게 설계되어 있다. |
| **CRN** (Common Random Numbers, 공통 난수) | 두 시스템(예: 모드 H0와 H1)을 비교할 때 **같은 seed 집합을 재사용**하는 분산 감소 기법. 같은 주문 시퀀스·같은 보행자 흐름에서 모드만 바꿔 비교하므로, "조건 차이"가 아닌 "모드 차이"만 깨끗하게 측정된다. 통계적으로는 짝지은(paired) 비교가 성립하여 검정력이 크게 올라간다. |
| **Replay 모드 vs Generative 모드** | Replay = 실제 데이터의 각 주문(발생 시각·조리 시간·부피 등)을 **그대로 재생**하여 시뮬레이션에 주입하는 방식(본 논문의 주력). Generative = 데이터에서 적합한 확률분포로부터 **합성 표본을 생성**하는 방식(스트레스 테스트 전용). |
| **V&V** (Verification & Validation, 검증과 타당화) | Verification = "모델이 설계대로 구현되었는가"(코드 검증), Validation = "모델이 현실을 타당하게 반영하는가"(현실 정합). 시뮬레이션 논문의 신뢰도를 결정하는 핵심 절차로, Sargent(2013)의 프레임워크가 표준 참고문헌이다. |
| **게이트 (A/B/C/D-게이트)** | 본 프로젝트에서 확립한 **자동 검증 배터리**의 이름. 시뮬레이션 결과가 반드시 만족해야 하는 불변식(보존 법칙, 시간 순서, 물리 정합 등)을 코드로 작성해 매 실행마다 자동 판정한다. A-게이트(**A1~A14**) = H0 모드용(완료 — v2 개정에서 A10~A12, R8에서 A13·A14 신설), B-게이트 = H1(로봇)용, C-게이트 = H2(큐잉)용, D-게이트 = H3(락커)용(각각 해당 Phase에서 신설). |
| **골든패스 (golden path) 테스트** | 주문 1~2건짜리 극소 시나리오에 대해 **손으로 계산한 예상 결과**(도착 시각, 대기 시간, 배달 완료 시각 등)와 시뮬레이션 기록이 tick 단위로 정확히 일치하는지 대조하는 테스트. H0에서는 5개 케이스 전부 0-tick 오차로 통과했다. |
| **비트 동일성 (bit-identical)** | 코드를 수정한 후에도 기존 기능의 출력이 바이트 수준까지 완전히 같음을 확인하는 게이트. 새 모드를 추가할 때 기존 H0 결과가 조금도 변하지 않았음을 증명하는 데 쓴다(무교란 증명). |
| **face validity (안면 타당성)** | 결과가 상식·도메인 직관과 부합하는지의 검사. 예: "라이더는 2층은 계단으로 가고 10층은 반드시 엘리베이터를 탄다"가 시뮬레이션에서 재현되는가. |
| **극한 테스트 / 단조성 테스트** | 극한 = 입력을 극단값(주문 0건, 보행자 10배 등)으로 밀었을 때 모델이 깨지지 않고 해석 가능한 거동을 보이는지. 단조성 = "엘리베이터가 빨라지면 배달이 빨라진다"처럼 방향이 자명한 인과가 시뮬레이션에서도 같은 방향으로 나오는지. |
| **G/G/c 큐잉 근사 (Allen–Cunneen 공식)** | 일반 도착분포(G)·일반 서비스분포(G)·서버 c대인 대기행렬의 평균 대기시간을 주는 해석적 근사 공식. ABM의 큐잉 구역(H2) 대기시간이 이 이론값과 ±20% 이내로 부합하는지 대조(docking)하여 모델을 독립 검증한다. |

### §0.2 데이터 용어 (배달의민족 라이더 데이터)

| 용어 | 설명 |
|---|---|
| **배민 데이터** | 배달의민족 라이더 배달 기록(JSON, `data/data1/` 39개 파일). 각 파일이 하나의 "시나리오"로, 서울 강남 일대의 실제 주문 묶음이다. 스키마 정의는 `data/data_ex.txt`가 정본. **이 중 본 연구가 쓰는 것은 28개**(K50~K300); K500·K750·K1000 11개는 보류(§1 결정 로그·`configs/scenario_tiers.yaml`). |
| **K (수요 강도)** | 한 시나리오에 든 주문 건수. K ∈ {50, 100, 200, 300, 500, 750, 1000}. 파일명 `K50_1.json` = "주문 50건짜리 시나리오 1번". |
| **주문률 (%/h)** | K를 빌딩 사무 상주인원(**900명** — 2~10F 각 100명)으로 나눈 시간당 주문 비율. K=50이면 **5.6%/h**, K=300이면 **33.3%/h**. 본 실험의 코퍼스는 **K50~K300(5.6~33.3%/h)** 이고 K500·K750·K1000은 보류다(§1 결정 #21). *2026-08-04 정정 — 구판의 "~800명 기준 6~63%/h"는 v1 빌딩(층당 800㎡·상주 800명)의 값이라 v2에서는 분모가 틀리다. `configs/scenario_tiers.yaml` 주석의 "약 6~38%/h"도 같은 구 분모로 계산된 값이다.* |
| **ORD_TIME** | 주문 발생 시각(초). 라이더 도착 시계열 합성의 출발점. |
| **COOK_TIME** | 식당의 음식 준비 시간(300~3,000초). 라이더는 조리 완료 후에야 픽업할 수 있다. |
| **VOL** | 주문 부피(5~100). 라이더 적재 용량, 락커 칸 크기, 로봇 적재 제약과 대조된다. |
| **DLV_DEADLINE** | 배민 알고리즘이 고객에게 약속한 배달 기한(절대 시각). 플랫폼의 SLA(§0.4) 기준선으로 쓴다. |
| **DIST** | 주문별 픽업지↔배달지의 실제 도로망 거리 행렬(m). 라이더의 빌딩 도착 시각 합성에 쓴다. |
| **RIDERS (BIKE/WALK/CAR)** | 라이더 유형 3종과 속성(속도 5.29/1.32/4.23 m/s, 적재 용량 100/70/200, 건당 변동비, 시나리오당 고정비, 처리 시간). 주문별 라이더 유형은 "그 부피를 실을 수 있는 유형" 안에서 가용 대수 가중으로 추출한다(capa-conditional 규칙, 검증 완료). |
| **라이더 도착 시각 합성식** | `t_rider_arrival = ORD_TIME + COOK_TIME + DIST/speed × ε` (ε = 로그정규 도로 혼잡 노이즈, σ=0.15). 도시 외부의 배달 과정을 추상화하지 않고 실데이터 그대로 시간축에 반영하는, 본 연구의 핵심 캘리브레이션(모수 보정)이다. 구현: `analysis/rider_arrival_model.py`. |
| **층 프로파일 (uniform / bottom_heavy / top_heavy)** | 주문의 목적층을 결정하는 건물 인구밀도 분포. uniform = 전 층 균등(기본), bottom_heavy = 저층 집중, top_heavy = 고층 집중. 도시 좌표와 빌딩 층 사이에 의미 있는 매핑이 없으므로 층 배정은 도시 데이터와 **완전 독립**으로 추출한다(time–space decoupled 원칙, §2.3). |
| **scenario_window** | KPI 측정 시간창을 "해당 시나리오의 주문 존재 구간 ± 1시간"으로 잡는 규약. 과거의 고정 시간창(legacy)은 고부하에서 혼잡을 최대 56% 과소평가함이 정량 확인되어(`results/vv/window_bias.csv`) 본문은 scenario_window로 확정. |
| **orderspan (주문 구간)** | 가동률·비용처럼 분모가 "측정 시간"인 KPI의 분모 규약. 본문 = [첫 주문, 마지막 배달] 구간, 부록에 전체 시간창 병기(확정 규약, `etc/note_kpiwin_convention.md`). |

### §0.3 모델 용어 (빌딩·에이전트·핸드오프 모드)

| 용어 | 설명 |
|---|---|
| **10F 빌딩** | 실험 환경. 한국 표준 중형 사무 빌딩: **지상 10층 + 지하 2층(B1·B2)**, 층당 **~1,200 m²**(사무실 12개/층), 층당 **100명** 상주(2~10F 합 **900명**, 지상층 포함 ~1,000명), 엘리베이터 **4대**(15인승), 복도 **34 m**. 지하 2개층은 **사람 승하차 전용**(사무공간 없음 — EV 이용률을 만드는 배경 부하원). 설정 파일: `configs/baseline_10f.yaml`. |
| **EV1~EV4** | EV = elevator(엘리베이터). 복도 중앙에 **교차 배치** — 북측 EV1·EV3 / 남측 EV2·EV4. **EV1·EV2 = 사람 전용, EV3·EV4 = 사람·로봇 공용**(`building.shared_ev_ids`로 선언적 지정). 로봇 1대가 타면 사람 정원이 15명 → 11명으로 줄어든다("정원 잠식"). 로봇은 **EV3·EV4만** 탈 수 있다. |
| **핸드오프 (handoff)** | 외부 배달 라이더가 빌딩 1층 로비에서 음식을 "누군가/무언가에게 넘기는" 행위. 이 넘김 방식이 본 연구의 조작 변수이며, 아래 4가지 모드로 정식화한다. |
| **H0 (Direct, 직접 배달)** | 로봇 없음. 라이더가 직접 엘리베이터(또는 저층이면 계단)로 올라가 사무실 문 앞까지 배달하고 내려와 퇴장. 현재 한국 오피스의 표준 관행이자 본 연구의 기준선(baseline). **구현·검증 완료.** |
| **H1 (Sync, 동기 핸드오프)** | 라이더가 로비 카운터에서 로봇에게 직접 인계(인계 시간 평균 60초, 표준편차 15초)하고 즉시 퇴장. 로봇이 **공용 EV(EV3·EV4)** 로 올라가 사무실에 인도(30초)하고 1층으로 복귀. 라이더와 로봇이 **동시에 만나야** 하며, 로봇이 전부 배달 중이면 라이더는 카운터 앞에서 **상한 없이 FCFS로 대기**한다(아무 정보 제공 없음 — 이 지점이 H2와의 유일한 차이. 2026-07-23 명문화). |
| **H2 (Informed, 알림 기반 핸드오프)** | H1과 같은 무상한 FCFS 대기이되, 라이더 도착 시 로봇이 모두 바쁘면 **빌딩 관리자가 예상 대기 시간 W_est를 알려준다**. 라이더는 W_est를 자신의 유형별 시간단가 w_R(§0.5)로 대기 비용으로 환산해, 비용 임계 **C_th** 이상이면 큐에 서지 않고 **즉시 직접 배달(H0 방식)로 전환**한다(사전 판단 balk — 진입 후 포기(renege)는 없음). 판단은 결정론(난수 불요), 대기열 명시 용량 상한 없음. 잔여 세부 규칙은 Phase B 착수 시 동결(§6 Phase B). *2026-07-23 확정 — 구 정의 "큐 용량 8 + τ_patience 5분 사후 포기"를 대체.* |
| **H3 (Locker, 자동 도킹 락커)** | 라이더가 로비의 락커(잠금 보관함)에 음식을 넣고(도킹 평균 20초) **즉시 퇴장** — 로봇을 기다릴 필요가 없다. 로봇이 나중에 락커에서 꺼내(15초) 배달. 락커가 만석이면 H2 경로로 우회(fallback — 알림·balk 규칙 동일 적용, 2026-07-23 정합). 락커 칸 수 M ∈ {2, 4, 8}, 칸 부피 상한 V_max, 최대 보관 30분. |
| **로봇 (RobotAgent)** | 실내 배달 로봇(Bear Robotics Servi, LG CLOi 등 시판 기종 사양 참조). 속도 1.0 m/s, 적재 100(부피 단위), 계단 이용 불가 → **저층 주문도 반드시 공용 EV(EV3·EV4)를 사용**해야 한다는 점이 핵심 제약. **대기와 충전이 모두 1층 로비 로봇존**에서 일어난다(대기＝충전, opportunistic — 지하 충전 도크는 개정 §1.3에서 폐지됐다. 충전 사이클 자체는 미모델링, §6 참조). |
| **보행자 (PedestrianAgent)** | 빌딩 상주 직원의 배경 통행. 점심 피크 상수 포아송 도착 **7.5명/분**(900명 × 0.5통행/h 캘리브레이션, 확정 규약). 지상측 종점은 **1F 0.50 / B1 0.30 / B2 0.20**으로 재분배된다(인원 증가가 아니라 **행선지 분산** — 같은 인원이 더 긴 구간을 타므로 EV 부하가 오른다). 연구의 종속변수가 아니라 **엘리베이터 혼잡을 만들어내는 배경 부하**다. |
| **계단 손실 효과** | H0에서 라이더는 2층 주문의 89.6%를 계단으로 처리하고 6층 이상은 0%다(`results/vv/face_stairs_by_floor.csv`). 로봇은 계단을 못 가므로, 로봇 모드(H1~H3)로 바꾸면 **저층 주문까지 전부 엘리베이터 수요로 편입**된다. H0 검증에서 발견된 비자명한 역전 메커니즘으로, 본 논문의 차별적 논점 중 하나. |
| **C_th (balk 비용 임계)** | H2에서 "기다림 vs 직접 배달"을 가르는 대기 비용 임계(원). balk 조건 = W_est × w_R(유형)/3600 ≥ C_th. 기본값 = BIKE 시간단가의 10분 등가(정확값은 STAGE 1 w_R에서 스크립트 산출), 민감도 스윕 {5, 10, 15}분 등가. 유형별 실효 시간 임계 τ_eff = C_th/w_R가 달라 고단가 유형(CAR)이 먼저 balk하는 이질적 행동이 실데이터 단가에서 창발한다. *구 τ_patience(renege 인내 임계, 5분)를 대체 — 2026-07-23.* |
| **빌딩 관리자 (BuildingManagerAgent)** | 관제의 로봇 상태 정보로부터 W_est(예상 대기)를 결정론적으로 계산해 H2 라이더에게 알림을 제공하는 **정보 제공자**. H3에서는 락커 보관 한도 초과 개입의 주체. 8-에이전트 목록(§3 C1)에 있던 역할이 2026-07-23 개정으로 실체화되었다. |

### §0.4 KPI (평가 지표) 용어

KPI(Key Performance Indicator) = 시스템 성능을 요약하는 핵심 수치. 본 연구는 세 이해관계자별로 KPI를 분리해 같은 시뮬레이션에서 동시에 산출한다.

| 용어 | 설명 |
|---|---|
| **T_lobby** [초] | **라이더 지표.** 라이더가 로비에 들어와서 나가기까지의 빌딩 체류 시간. 짧을수록 라이더가 다음 주문을 빨리 받을 수 있다(긱 노동 후생). |
| **T_e2e** [초] | **고객 지표.** end-to-end — 주문 발생부터 고객이 음식을 받기까지의 총 시간. 평균과 p95를 함께 보고한다. |
| **p95 (95퍼센타일)** | 전체 관측치 중 하위 95%가 이 값 이하라는 뜻. "최악에 가까운 5% 경험"을 대변하므로 평균보다 고객 체감에 민감한 꼬리 지표다. |
| **W_EV** [초] | 엘리베이터 호출 후 탑승까지의 평균 대기시간. 수직 수송 병목의 직접 지표이며, **EV1~EV4를 분리 보고**한다. ⚠️ **2026-08-11(결정 #31)**: **보행자**의 W_EV는 **타당성 가드**다 — 모드 간 차이가 ±1~6 s로 주 지표의 1/1000이고 고부하에서 부호가 H1에 유리하다. 수직 경합의 본 지표는 **로봇의 W_EV**(배달당 왕복 60~75 s, `T_building_order`의 임계 경로) + `robot_board_denied`이며, 보행자 EV별 분리는 "보행자가 공용 카를 회피해 로봇이 빈 샤프트를 물려받지 않았는가"를 확인하는 용도로 존치한다. |
| **SLA / L_sla_violation** | SLA(Service Level Agreement) = 플랫폼이 고객에게 약속한 배달 기한(= DLV_DEADLINE). L_sla_violation = 그 기한을 어긴 주문의 비율. **주의(검증 발견):** 배민 데이터의 기한이 넉넉해 K≤500에서는 위반이 사실상 0(40,350건 중 14건, 전부 K1000)이므로 본문 비교의 1차 지표로 쓸 수 없다(`results/vv/face_slack.csv`). |
| **deadline counterfactual (기한 강화 반사실 분석)** | 위 SLA 판별력 문제의 해법. 시뮬레이션을 다시 돌리지 않고, 이미 기록된 주문별 배달 시간에 대해 "기한이 지금보다 x분 짧았다면 위반율이 얼마였을까"를 후처리로 계산하는 분석. |
| **S_customer** | 고객 만족도 프록시 = σ(−β·max(T_e2e − 기한, 0)). 기한 내 도착이면 0.5, 초과 시 초과분에 비례해 감소. SLA와 같은 판별력 한계를 가지므로 부록 보고용. |
| **U_robot / U_locker** | 로봇 가동률 / 락커 점유율. 자원 투자 대비 활용도의 지표(분모는 orderspan 규약, §0.2). |
| **W_rider / R_handoff** | 라이더의 시간당 실효 소득(원/h) / 시간당 처리 가능 주문 수. T_lobby를 화폐화한 라이더 후생 지표. |
| **L_rider_balk / 알림 지표** | H2 전용(2026-07-23 신설, 구 L_rider_abandon 대체). L_rider_balk = 관리자 알림을 받고 직접 배달로 전환한 주문 비율 — "로봇 인프라가 흡수하지 못한 수요"의 직접 지표. 보조: 알림 건수, 라이더 대기 비용 합계(원), W_est 예측 오차(예상 vs 실현 대기, report-only — 정보 품질 논의 재료). |

### §0.5 경제성 분석 용어

| 용어 | 설명 |
|---|---|
| **CAPEX / OPEX** | CAPEX(Capital Expenditure) = 초기 설비 투자비(로봇 구매, 락커 설치). OPEX(Operating Expenditure) = 운영비(유지보수, 전기료). |
| **NPV** (Net Present Value, 순현재가치) | 미래 5년간의 수입·비용 흐름을 할인율(기본 5%)로 현재 가치화해 합산한 값. 모드별 인프라 투자의 경제성을 비교하는 빌딩 관리자 관점의 최종 지표. |
| **w_R (라이더 시간단가)** | 라이더 1시간의 기회비용(원/h). 배민 RIDERS 테이블에서 캘리브레이션: BIKE 기준 약 10,500원/h, 민감도 범위 [5,000, 20,000]. 라이더의 빌딩 체류 시간을 돈으로 환산할 때 쓴다. |
| **break-even w\*** | "라이더 시간단가가 얼마 이상이면 락커(H3) 투자가 동기 핸드오프(H1)보다 이득이 되는가"의 손익분기 단가. NPV_H3(w\*) = NPV_H1(w\*)의 해. |
| **break-even λ\*** | "수요가 얼마를 넘으면 우세 모드가 바뀌는가"의 손익분기 수요 강도. |

### §0.6 통계·분석 용어

| 용어 | 설명 |
|---|---|
| **paired 검정 (paired t / Wilcoxon)** | 같은 조건(같은 seed·같은 주문 시퀀스)에서 모드만 바꾼 짝지은 표본의 차이를 검정하는 방법. CRN 설계(§0.1)와 결합하면 조건 간 잡음이 소거되어 검정력이 높다. Wilcoxon = 정규성 가정이 필요 없는 비모수 버전. |
| **Holm 보정** | 여러 쌍(4개 모드면 6쌍)을 동시에 검정할 때 우연히 유의해 보이는 오류(다중비교 문제)를 통제하는 p-값 보정법. |
| **ANOVA + Tukey HSD** | 여러 집단 평균의 차이를 한 번에 검정(ANOVA)하고 어느 쌍이 다른지 사후 비교(Tukey)하는 고전적 방법. CRN 설계와는 독립성 가정이 어긋나므로 본 연구에선 **보조 보고**로만 쓴다(§8.3). |
| **bootstrap CI (B=1000)** | 데이터를 1,000번 재추출(resampling)해 신뢰구간(CI, Confidence Interval)을 수치적으로 얻는 방법. break-even 값처럼 분포를 해석적으로 못 구하는 통계량에 쓴다. |
| **Pareto frontier (파레토 경계)** | 세 이해관계자 지표를 동시에 볼 때 "어느 한쪽을 희생하지 않고는 다른 쪽을 개선할 수 없는" 비지배 해들의 집합. 모드 간 삼자 균형을 시각화하는 틀. |
| **hypervolume / ε-dominance / C-metric** | Pareto 경계의 품질을 숫자 하나로 요약하는 지표들. hypervolume = 기준점 대비 경계가 덮는 부피(클수록 좋음), ε-dominance = 비지배 점 빈도, C-metric = "모드 A의 해가 모드 B의 해를 몇 % 지배하는가"의 집합 커버리지. |
| **Morris / Sobol 민감도 분석** | 모델의 12개 입력 파라미터 중 어느 것이 결과를 크게 흔드는지 정량화하는 전역(global) 민감도 기법. Morris = 저비용 스크리닝(1차 선별), Sobol = 선별된 상위 파라미터의 분산 기여율 정밀 산출. 파이썬 SALib 패키지로 구현. |
| **LHS** (Latin Hypercube Sampling) | 파라미터 공간을 고르게 덮도록 표본을 뽑는 실험계획 기법. Morris/Sobol의 입력 생성에 쓴다. |

## §2. 연구 개요 — 무엇을, 왜 연구하는가

### §2.1 배경과 문제의식

AI 자율주행 배달 로봇의 빌딩 내 식음료 배달이 상용화 단계에 진입했다(Bear Robotics
*Servi*, LG *CLOi ServeBot*, 우아한형제들 *Dilly Drive*). 동시에 도시의 라스트마일
배달은 배달의민족 등 플랫폼의 인간 라이더가 담당한다. 이 두 시스템이 만나는 유일한
접점이 **빌딩 로비의 핸드오프**(라이더 → 로봇/락커로 음식을 넘기는 순간)인데, 현실에서
매일 수천 건씩 일어나는 이 접점이 학술적으로는 거의 다뤄지지 않았다:

- 실내 로봇 배달 연구는 빌딩 내부만 모델링하고 외부 도착을 단순 포아송 과정으로 추상화한다.
- 라스트마일 물류 연구는 도시 측 경로 최적화에 집중하고 빌딩 내부의 "마지막 100 m"를 점 하나로 축약한다.
- 택배 락커 연구는 위치·크기 최적화에 집중하고 **식음료의 실시간 라이더 회전율**과 결합된 분석이 없다.

핸드오프 방식의 선택은 세 이해관계자의 시간과 돈을 동시에 재배분한다: **라이더**는 빌딩
체류가 길수록 시간당 소득이 준다(긱 이코노미 후생), **고객**은 핸드오프 지연이 배달
시간과 만족도로 직결되고, **빌딩 관리자**는 로봇·락커의 투자비(CAPEX)와 운영 효익
사이에서 NPV 균형을 잡아야 한다.

### §2.2 벤치마크 논문과 본 연구의 위치

방법론적 벤치마크는 **세종시 공공자전거(어울링) 데이터 기반 ABM 논문**이다(상세 요약:
`archive/h0_v1/docs/extension_suggestion.md`). 그 논문이 (1) 1년치 실측 대여 데이터로 확률분포를
캘리브레이션하고, (2) 사용자·스테이션 에이전트의 상향식 상호작용으로 시스템을 재현하고,
(3) 관리자의 실제 고민(스테이션 교체, 적정 자전거 대수)에 정량 가이드라인을 준 것과
정확히 같은 구조로, 본 연구는 (1) 배민 실측 주문 데이터로 라이더 도착·조리·부피·기한을
캘리브레이션하고, (2) 라이더·로봇·락커·고객·보행자·엘리베이터의 상향식 상호작용으로
로비 핸드오프 생태계를 재현하고, (3) 빌딩 설계자의 실제 고민(어떤 핸드오프 방식? 로봇·
락커 몇 대?)에 정량 가이드라인을 제공한다.

### §2.3 핵심 방법론적 입장 — time–space decoupled calibration

배민 데이터는 도시(강남구) 좌표계의 기록이고 시뮬레이션 무대는 가상의 10층 빌딩이다.
도시 위경도와 빌딩 층 사이에는 의미 있는 대응이 없으므로, **시간 구조(주문 발생·조리·
이동·기한)는 데이터를 그대로 이식하고, 공간 구조(목적층·호실)는 빌딩 인구밀도
프로파일에서 독립적으로 추출**한다. 이 분리 원칙은 좌표 역식별 위험 회피(§11)와도
일관된다.

### §2.4 연구 제목(안)과 타겟 저널

**제목(안)**: *"A Multi-Stakeholder Agent-Based Simulation of Robot-Mediated Lobby
Handoff in Smart Buildings: Comparing Direct Delivery, Synchronous Handoff, Informed
Handoff, and Autonomous Docking Lockers under Real Demand Patterns"*
(H2 표기는 2026-07-23 balk 개정에 따라 "Queued"→"Informed"로 변경 — Phase F에서 최종 재확정)

**타겟 저널**: 1순위 **SMPT**(Simulation Modelling Practice and Theory, IF ~4.0) —
데이터 기반 시뮬레이션 + 실무 해법이라는 저널 성격에 최적합. 리젝 시 대안: Computers &
Industrial Engineering(IF ~7.2, 운영·비용 색채 강화), Transportation Research Part
E(IF ~10.6, 긱 후생·라스트마일 색채 강화).

### C1. 방법론적 기여 — 전체 서비스 생태계의 상향식 통합 모델 + 재사용 가능한 검증 체계

**주장**: 기존 배달 로봇 연구가 로봇 단독의 경로 최적화에 머문 반면, 본 연구는
라이더 → (로봇|락커) → 고객으로 이어지는 전체 생태계를, 배경 보행자와 엘리베이터
자원 경합까지 포함해 하나의 ABM으로 최초 통합했다.

**실증 수단**:
- 8-에이전트 시스템(고객·외부라이더·로봇·락커·빌딩관리자·관제·엘리베이터·보행자) + 4-모드 디스패처의 완전한 프로세스 모델(§6 각 Phase에서 구현). 특히 빌딩관리자는 관제의 로봇 상태로부터 예상 대기 W_est를 산출해 라이더에게 제공하는 **정보 제공자**로 실체화되어(H2, 2026-07-23 개정), "스마트 빌딩의 관제 지능이 인간-로봇 접점을 조정한다"는 제목의 서사를 에이전트 수준에서 구현한다.
- **모드별 검증 게이트 배터리(A/B/C/D-게이트)**: H0에서 확립한 **14개** 자동 불변식 게이트(A1~A14)·골든패스·극한/단조성/결정성 테스트 체계를 신규 모드마다 복제·확장한다. 이 "replay 기반 ABM을 위한 V&V 템플릿" 자체가 Sargent(2013) 프레임워크에 *외부 입력 시계열 검증*과 *비트 동일성 무교란 게이트*를 추가한 방법론 기여로, SMPT의 방법론 지면에 정면 배치한다.
- 검증의 정직성을 보여주는 발견·수정 이력 공개(H0에서 8건, `archive/h0_v1/docs/verification_report_h0.md` §3) — "검증이 실제로 결함을 잡았다"는 실효성 증거.

### C2. 데이터 기반 현실성 — 배민 실측 수요의 per-order 재생 캘리브레이션

**주장**: 수학적 가정이 아니라 한국 1위 배달 플랫폼의 실측 주문 **28개 시나리오
(5,200건)** 을 주문 단위로 재생(Replay)하여, 점심 피크의 현실 수요 아래에서
모드를 비교했다.

> **모집단 정정 (2026-08-04)**: 구판은 "39개 시나리오(13,450건)"였다. 보유 데이터는
> 여전히 39개 파일이지만, K500·K750·K1000(11개)은 본 실험에서 **보류**하기로
> 확정돼(주문률 ~63~125%/h로 본 연구의 대상 범위를 넘음) 모델링·인용 모집단은
> 28개·5,200건이다. 논문에 39/13,450을 쓰면 실제 실행하지 않은 데이터를
> 근거로 제시하는 것이 되므로 **반드시 28/5,200으로 인용**할 것.

**실증 수단**:
- STAGE 1 캘리브레이션(완료): 조리 시간 Gamma 적합(AIC 최우수), 라이더 유형 capa-conditional 추출(부피 제약 위반 0/52,000), 라이더 도착 시각 합성식, 시간단가 w_R 환산 — `analysis/rider_arrival_model.py`, `STAGE1_summary.md`.
- 데이터 무결성 전수 검사(중복 1쌍 검출·제외, 부피 상한 위반 0건 — `results/vv/data_integrity.csv`).
- **검증 발견의 정직한 반영** — 리뷰어가 지적하기 전에 논문이 먼저 밝힌다: ① 배민 기한이 넉넉해 SLA 위반율은 본문 부하에서 판별력이 없음 → 기한 강화 counterfactual로 대체(§4) ② 측정 시간창 선택이 혼잡 지표를 최대 56% 바꿈 → scenario_window 채택 근거 정량 제시 ③ 엘리베이터 배차 휴리스틱의 차선 선택 비용이 평균 6.36초로 유계임을 계측으로 방어(`results/vv/evsel_stale.csv`).

### C3. 실무적 기여 — 스마트 빌딩 설계자를 위한 의사결정 가이드라인

**주장**: 빌딩 규모·수요 수준에 맞춰 "어떤 핸드오프 방식을, 로봇·락커 몇 대로 도입할지"를
읽어낼 수 있는 정량 가이드라인을 제공한다 — 벤치마크 논문이 "적정 자전거 대수"를 제시한
것의 빌딩 버전.

**실증 수단** (확정: 가이드라인 표 + 재현 패키지, 대시보드 미포함):
- **모드 추천 표**: 수요 K(6~63%/h) × 층 프로파일(uniform/bottom/top) 격자별 우세 모드와 KPI 근거.
- **경계 히트맵**: 모드 간 우열이 뒤집히는 수요·프로파일 경계면의 시각화(figure).
- **자원 sizing**: 로봇 대수 {2, 3} × 락커 칸 수 M {2, 4, 8} × 칸 부피 V_max {50, 70, 100} 스윕의 적정점.
- **break-even 공식**: 락커 투자가 이득이 되는 라이더 시간단가 w\*와 수요 λ\*의 폐형식 해 + bootstrap 신뢰구간.
- **재현 패키지**: 전체 코드·설정·seed·실행 스크립트를 GitHub + Zenodo DOI로 공개, config 기반 CLI로 임의 빌딩 스펙 재실험 가능.

## §4. 연구 질문(RQ)과 평가 지표

구 계획서의 RQ 골격을 유지하되, H0 검증 발견에 맞춰 지표와 통계 방법을 재편했다.
변경점은 각 RQ에 명시한다.

**RQ1 — 4가지 핸드오프 모드 간 성능 차이는 통계적으로 유의한가?**
- 1차 KPI: T_lobby(라이더 체류)·T_e2e p95(고객 꼬리)·W_EV(엘리베이터 대기, **전용 EV1·EV2 / 공용 EV3·EV4 분리**).
- 통계: **CRN 페어드 설계** — 4모드에 동일 seed 집합 {1..30} 재사용, 모드 쌍별 차분의 paired t/Wilcoxon + Holm 보정(6쌍). ANOVA+Tukey는 관례적 보조 보고(§8.3).
- *변경 근거*: 구 계획의 1차 KPI였던 SLA 위반율은 본문 부하(K≤500)에서 위반이 사실상 0이라 판별력이 없음이 확정됨(V5b CAUTION, `results/vv/face_slack.csv`). SLA·만족도는 부록 스트레스 트랙(K1000)과 deadline counterfactual로 이동.

**RQ2 — 수요가 6%/h(K=50)에서 63%/h(K=500)로 증가하면 우세 모드가 전환되는가? 전환 메커니즘은 무엇인가?**
- K-계층별 우세 모드 판정 + 전환점 검출.
- 메커니즘 분해: 배달 시간의 성분 분해(조리/라이더대기/이동/EV대기/인계/인도 — H0에서 잔차 float-exact로 검증된 분해 체계를 4모드로 확장)로 "왜 뒤집히는지"를 계량. 특히 **계단 손실**(로봇 모드에서 저층 주문의 EV 수요 편입), **정원 잠식**(공용 EV3·EV4 15→11), **호출 배증**(로봇 왕복 = 주문당 공용 EV 호출 2회), **정보 개입**(H2의 관리자 알림 balk 전환 — balk된 주문은 사실상 H0 서브모집단을 형성, 2026-07-23 추가)의 네 채널을 분리 보고.

**RQ3 — 라이더·고객·빌딩 3-이해관계자 Pareto frontier의 형태는? 어느 모드가 균형점을 차지하는가?**
- 3차원 목적(W_rider, 고객 지표, BuildingNPV) 공간에서 4모드 × 5 K = 20점의 Pareto 분석.
- 지표: hypervolume, ε-dominance 빈도, C-metric(집합 커버리지). 시각화: 3D 산점 + 2D 투영 3면.

**RQ4 — 락커(H3) 투자의 손익분기점은?**
- break-even 라이더 시간단가 w\*: NPV_H3(w\*) = NPV_H1(w\*)의 해(w_R에 선형이므로 폐형식으로 유도 가능).
- break-even 수요 λ\*: 모드 지배가 뒤집히는 수요 강도(hypervolume 부호 전환점).
- 불확실성: seed 30개 기반 bootstrap(B=1000) 신뢰구간 + w\*의 K-민감도.

### Phase B (주 4~6): H2 알림 기반 핸드오프(balk) + C-게이트 + 큐잉 이론 대조

> *2026-07-23 전면 개정 — 구판(큐 용량 8 + τ_patience renege)은 §1 결정 #11~#15로 대체.
> Step 단위 상세는 `etc/scie_phase/phase_B_h2_queue.md`(동일 날짜 개정판)를 따른다.*

**왜**: H2는 "로봇이 부족할 때 스마트 빌딩의 관제 정보가 라이더의 선택을 바꾼다"는
현실적 중간 형태다. 빌딩 관리자가 예상 대기 W_est를 알려주고, 라이더가 유형별
시간단가로 환산한 대기 비용이 임계 C_th 이상이면 기다리지 않고 직접 배달로 전환한다
(사전 판단 balk — 대기 손실 후 포기하는 renege가 아님). H1과의 유일한 차이가 정보
제공이므로 CRN 페어드 차분이 곧 **"관리자 정보 개입의 가치"**로 해석된다. 또한 구 계획
8-step V&V 중 유일하게 미실시였던 step 5(G/G/c 큐잉 대조)를 이 Phase에서 실행한다 —
1차 대조 대상은 이론 가정(전원 진입·무한 인내)에 정확히 부합하는 **H1**(Phase A 배터리
기록 재사용), H2는 balk 절단 큐로 보조 대조.

**무엇을**:
1. **착수 시 잔여 설계 동결(사용자 확인 1회)** — 핵심 메커니즘은 §1 #11~#15로 기확정. 잔여: ①W_est 산식 상수(로봇별 잔여 작업의 결정론 성분 합산 + EV 대기 성분의 최근 이동평균 창 크기 — 기록으로부터 재현 가능해야 함) ②C_th 정확값(STAGE 1 w_R의 BIKE 10분 등가를 스크립트 산출해 config 기록) ③기록 스키마(`w_est_sec`·`balk_cost_krw`·`balk_h0` additive 필드).
2. 무상한 FCFS 큐 + 관제 W_est 계산 + 빌딩 관리자 알림 이벤트 + balk→H0 전환 경로(balk 시점부터 H0 라이더와 동일 FSM) 구현. balk 판단은 결정론 — **신규 난수 스트림 불요, CRN 무교란 자동**. KPI = L_rider_balk(유형별 분해)·알림 건수·대기 비용·큐 길이 p95.
3. **C-게이트 신설**(C1~C9): B-게이트 항목 + balk 전용 불변식 — 큐 보존(도착 = 즉시 인계 + 진입 + balk; 진입 = 인계), FCFS 위반 0, balk 정합(모든 balk에서 비용 ≥ C_th·모든 진입에서 < C_th, 유형별 재계산), W_est 결정론 재현, balk 라이더의 H0 불변식 정합. 큐 길이 p95는 face-validity 보고(상한 게이트 없음).
4. **G/G/c docking**: H1 기록을 Allen–Cunneen 근사와 ±20% 대조(1차) — 실효 서비스 시간 = 인계 + 로봇 왕복 점유로 유도, 정상상태 구간 절단 규약 유지. H2는 진입자 조건부 대기로 보조 대조(절단의 하향 편향 방향 명시). 비부합 구간은 비정상성 논거와 함께 투명 보고(리뷰어 사전 방어).
5. H2 골든패스 2케이스(W_est 수기 계산 ≥ 임계 ⇒ balk ⇒ H0 완주 케이스 포함, 유형 단가 포함 0-tick 대조), 단조성(C_th↑ ⇒ balk율↓, 로봇 수↑ ⇒ balk율·큐 대기↓, K↑ ⇒ balk율↑, 유형별 balk율 = 단가 순), 극한(**C_th=∞ ⇒ H2≡H1 비트 동일** — balk 배선의 강력한 자기 검증, C_th=0 ⇒ busy 도착 전원 즉시 H0), **28×3 = 84 run** 배터리.

**산출물·게이트**: H0·H1 비트 동일 유지, C-게이트·골든패스·배터리 PASS, G/G/c 대조 결과표(H1 1차 + H2 보조, 부합/비부합 구간 명시).

### Phase C (주 6~8): H3 자동 도킹 락커 + D-게이트 + 락커 sizing

**왜**: H3는 라이더가 로봇을 기다리지 않는 유일한 모드(비동기 핸드오프)로, 라이더
후생에 가장 유리하지만 락커 CAPEX가 든다 — RQ4 break-even 분석의 주인공이다.

**무엇을**:
1. **착수 시 설계 동결**: 락커 만석 fallback→H2 진입 시점 규약(fallback 라이더도 알림·balk 규칙을 그대로 적용받는다 — 2026-07-23 개정 정합), 보관 30분 초과 이벤트 처리(권장: 관리자 개입 이벤트로 기록만, 주문은 지연 인도), 로봇의 락커 수거 우선순위(권장: 보관 시간 최장 우선), 부피 배정 규칙(빈 칸 중 V_max ≥ VOL 최소 칸).
2. LockerAgent 구현: 칸 상태 배열, try_dock(20±5초)/notify/pickup(15±4초), 점유율·도킹 실패율 계측.
3. **D-게이트 신설**: 락커 보존(도킹 = 수거 + 잔여), 부피 위반 0, fallback 경로 정합, 보관 한도 이벤트 정합.
4. H3 골든패스(도킹 즉시 퇴장 + 로봇 지연 수거 케이스), 단조성(M↑ → 도킹 실패율↓), 극한(M=1, V_max < VOL 최빈값), **28×3 = 84 run** 배터리.
5. **E4 락커 sizing 스윕**: M ∈ {2,4,8} × V_max ∈ {50,70,100} × K ∈ {50,100} — C3 가이드라인의 락커 축 재료.

**산출물·게이트**: 전 모드 비트 동일 유지, D-게이트·배터리 PASS, sizing 스윕 CSV.

### Phase D (주 9~11): 4-모드 통합 실험 + 경제층(costs.py)

**왜**: 여기서 논문 본문 결과가 전부 생산된다.

**무엇을**:
1. **본문 CRN 페어드 스윕**: 4모드 × **28 시나리오** × 30 seed = **3,360 run** (동일 seed 집합 {1..30}을 4모드에 재사용 — paired 설계). 전 run에 해당 모드 게이트 인라인 적용. H0 실측(1.01~2.13 s/run)을 그대로 외삽하면 직렬 **1.5시간 내외**이고 로봇 모드는 그보다 늘어난다 — 여전히 제약이 아니다.
2. **부록 스트레스 트랙**: 4모드 × 5 시나리오(K750×1, K1000×4) × 30 seed = 600 run — SLA 위반·한계 거동은 여기서만 보고.
3. **층 프로파일 축**: bottom_heavy/top_heavy를 K ∈ {100,300,500}에 추가(계단 손실 효과의 형태학 축 — 저층 집중일수록 로봇 모드의 EV 편입 손실이 커진다는 가설 검정).
4. **자원 스윕**: 로봇 대수 {2,3} × K ∈ {100,300,500}; 라이더 시간단가 w_R ∈ {5k,10k,15k,20k}원/h(후처리 가능 — T_lobby 화폐화라 재실행 불요. 단 H2의 balk 판단 단가는 STAGE 1 캘리브레이션 값으로 고정 — 후처리 스윕은 후생 화폐화 계수만 변경, 2026-07-23 규약).
5. **deadline counterfactual**: 기록된 주문별 T_e2e에 대해 기한을 −10/−15/−20분 강화했을 때의 가상 위반율 곡선(후처리).
6. **costs.py 구현**: 모드별 CAPEX(H0=0, H1/H2=로봇, H3=로봇+락커) + OPEX(유지보수 5%/y, 전기료) + 5년 NPV(할인율 5%) + **break-even w\* 폐형식**(w_R 선형 → 근찾기 불요: w\* = 연금화 ΔCAPEX·고정 OPEX ÷ 연간 ΔT_lobby). 연간 환산 = 점심 피크 1식 × 250 영업일(HR 트랙 R0-7 규약 승계). 수기 계산 대조 테스트로 `tests/test_cost_model.py` skip 해제.

**산출물**: `results/scie/` 통합 CSV, NPV·break-even 표, counterfactual 곡선.

### Phase E (주 11~13): 민감도 분석 + Pareto + 논문 figure 일체

**무엇을**:
1. **Morris 스크리닝**: 12 파라미터(w_R, 락커 M·V_max·도킹 시간, **C_th(balk 비용 임계 — 구 τ_patience 대체, 2026-07-23)**, 로봇 대수, K, 할인율 r, 사회적 수용성 α, 락커 CAPEX, 노이즈 σ_ε 등) × 10 궤적 — 영향 순위 1차 선별.
2. **Sobol total-order**: Morris 상위 6개 파라미터의 분산 기여율 정밀 산출(SALib). Tornado plot으로 KPI별(T_e2e, W_rider, NPV, hypervolume) 보고.
3. **Pareto 분석**: 3차원(W_rider, 고객, NPV) frontier + hypervolume/ε-dominance/C-metric + 3D·2D 투영 figure.
4. **논문 figure/table 전량 생산**(목록은 §9.2) — 전부 스크립트 자동 생성(수기 수치 금지, 레포 관례).

### Phase F (주 13~18): 집필·내부 검증·투고 (+버퍼 2주)

**무엇을**:
1. **4-모드 검증 리포트**: `etc/verification_report_4mode.md` — H0 리포트와 동일 형식으로 B/C/D-게이트·골든패스·배터리·발견 이력 집계. 논문 V&V 절의 원천.
2. **집필**: §9.1 구성안대로. 방법·검증 절 우선(재료 확정분) → 결과 절(Phase D/E 산출) → 서론·문헌(11개 키워드 클러스터, 30~45편) → Discussion·한계.
3. **내부 검증**: 본문 인용 수치 전수를 결과 CSV와 대조(스크립트 grep 대조 — H0 검증에서 확립한 관례), 용어·기호 일관성 패스.
4. **투고 준비**: SMPT 포맷팅, highlights 3~5줄, cover letter(기여 3건 + 검증 체계 강조), 재현 패키지 Zenodo DOI 발급, Data Availability 절.
5. **버퍼(2주)**: 지연 흡수. 리비전 대응은 일정 외(§10 리뷰어 예상 공격 참조).

구 계획의 "8-step Partial V&V"를 4-모드 체계로 갱신한다. 실측 운영 데이터가 없는 신생

>    편향된다. 규모는 `n_in_building_at_end`로 매 run 기록되며 **7.5/분에서 1~15명**
>    (K50_1 기준 15/808 = 1.9%), 30/분에서는 ~60명이다. **보행자 대기를 인용하는
>    문장에는 반드시 절단 편향을 병기**할 것.
> 6. **모델의 적용 범위에 상한이 있다 — 60/분 배경은 종료하지 않는다.** 컷오프가
>    없으므로 EV 용량을 넘는 배경 부하는 영원히 배출되지 않고 건물 내 보행자가
>    발산한다(overrun 28,800 s에서도 cap 트립, 3,614 → 10,072명). **이건 결함이
>    아니라 경계**이며, 포화 실험의 상한을 30/분으로 잡은 이유다. 논문 한계 절에
>    "본 모델은 EV 수직 용량 이내의 배경 부하에 대해서만 정상 상태를 갖는다"로
>    명시할 것.
>
> **주 지표 표기 규약**: 엘리베이터 이용률은 **`utilization_delivery`**(창 =
> [첫 주문, 마지막 라이더 퇴장])를 쓴다. 전 구간 `utilization`은 워밍업 머리를
> 분모에 포함해 4.6~7.5 %p 낮으므로 **진단용**이다. 그리고 이 지표는 **시간
> 가동률이지 적재율이 아니다** — 같은 run의 평균 재차 인원은 4대 합계
> **2.9~4.8명 / 정원 60석(4.8~8.0%)** 이다. 85%를 적재율로 읽으면 정반대 결론이
> 나오므로 `mean_passengers_delivery`를 항상 병기할 것.

**30 seed 근거 (2026-08-04 v2 재측정, `results/vv/variance_summary.csv`)**: n=30에서
95% CI 반폭이 **T_e2e 평균 ≤0.102% · T_e2e p95 ≤0.300% · T_lobby ≤0.944% ·
최광폭 W_EV ≤4.54%**(K50_1, 저부하일수록 넓다)로, H0 v2에서 관측된 처리효과 규모
(수요 방향 W_EV **+57.0%** K50→K200, **+20.2%** K200→K300)보다 한 자릿수 이상 작다.
모드 간 차이가 CI 반폭의 3배 미만으로 좁혀지는 대조에선 CRN 페어링을 우선 적용하고,
그래도 부족하면 해당 대조만 50 seed 상향.

> ⚠️ **CRN 이득을 전제하지 말 것 (W5e, 구판 주장 철회)**: `floor_seed` 고정 CRN의
> 분산 감소 채널비는 평균계 **0.394~1.217**, p95 **0.995~1.779**로 흩어져 **대부분
> 1.0과 통계적으로 구별되지 않는다**(n=30에서 분산비는 F(29,29), 95% 범위 ≈
> [0.48, 2.09]). 명확한 감소는 K300_4뿐이다. 구판의 "분산 30~65% 제거"는 **철회**됐다.
> Phase E는 "CRN이 이득을 준다"가 아니라 **"이득 여부를 시나리오별로 먼저 확인한다"**를
> 전제로 설계할 것.

### §8.2 CRN 페어드 규약 (H0 검증 V5d/V5e에서 확립, 승계)

- 전 처리 암에 동일 `rng_seed` 집합 {1..30} 재사용.
- 난수 스트림은 용도별 태그 분리(층 배정 `[0x666C6F72, floor_seed, ord_id]`, 핸드오프 `[0x686F6666, rng_seed, ord_id]` 등) — **신규 모드는 새 태그 스트림만 추가**하므로 기존 도착·층·수단·보행자 난수가 모드 간 완전 동일하게 유지된다(주문 단위 쌍 정렬 성립).
- 한계 보고: 큐·풀처럼 동적으로 진화하는 내생 상태는 모드 간 완전 쌍대조가 부분적으로만 성립 — 채널 분해와 함께 명시(H0 V5e 관례).

### §8.3 통계 방법

1. **1차**: 모드 쌍(6쌍)별 paired 차분의 평균·95% CI, paired t + Wilcoxon(정규성 방어), Holm 보정. 효과 크기(Cohen's d_z) 병기.
2. **보조**: 4-way ANOVA + Tukey HSD — 리뷰어 관례 대응용으로 병기하되, CRN에 의한 관측치 상관으로 독립성 가정이 보수적으로 어긋남을 각주 명시.
3. **break-even·hypervolume 불확실성**: 시나리오·seed 단위 bootstrap B=1000.
4. **다중 KPI**: 1차 게이트 KPI 3종(T_lobby, T_e2e p95, W_EV)에 한정해 가설 검정, 나머지는 기술 통계 보고(다중성 인플레 방지).

### §8.4 KPI 보고 규약

- 시간창: scenario_window(주문 구간 ±1h) — legacy 창 인용 시 편향 방향·크기 각주(K1000에서 W_EV −56%, `results/vv/window_bias.csv`).
- 가동률·비용: orderspan 분모 본문 + 풀 윈도우 병기(EV 가동률은 어느 정의든 92~98%로 결론 불변임을 각주 — `etc/note_kpiwin_convention.md`).
- 배차 휴리스틱 방어: 지정 배차의 차선 선택 비용이 평균 6.36초/p95 17초로 유계(`results/vv/evsel_stale.csv`) — 최적성 지적에 대한 정량 답변으로 방법 절에 선제 배치.
